# ux-copy-editor

Используй этот skill, когда текст уже написан, но ещё не готов к выпуску.

Это не генератор красивых формулировок.
Это финальный editorial layer в общей execution system, который доводит user-facing copy до боевого состояния перед user review или release.

## Роль в системе

`ux-copy-editor` работает как финальный copy-quality pass внутри core workflow:

- planning определяет задачу и контекст
- execution создаёт решение и черновой текст
- review проверяет качество результата
- `ux-copy-editor` доводит user-facing copy до релизного уровня
- после этого результат идёт на user review, refinement или release

Если текст видит пользователь, его нельзя считать завершённым без сильного editorial pass.

## Что считается user-facing text

Этот skill применять для:

- UI copy
- button labels
- menu items
- field labels
- placeholders
- helper text
- empty states
- error states
- validation messages
- toasts
- alerts
- confirmation dialogs
- onboarding copy
- settings copy
- product guidance
- microcopy
- short instructions
- system messages
- коротких текстовых блоков внутри фичи или user flow

При необходимости также использовать для коротких product/comms fragments, если они напрямую влияют на UX.

## Главная задача

Сделать текст:

- ясным
- коротким, где можно коротко
- точным
- естественным
- не AI-похожим
- не многословным
- не канцелярским
- полезным в конкретном интерфейсном контексте
- готовым к review или release

## Когда использовать

Используй этот skill, когда:

- текст уже существует
- текст звучит сыро
- текст перегружен
- текст слишком общий
- текст слишком “добренький”
- текст слишком формальный
- текст не даёт ясного next step
- текст выглядит как AI draft
- текст почти нормальный, но не дотягивает до product quality bar
- после implementation или refinement нужен финальный copy pass
- перед релизом нужно убедиться, что пользователь увидит сильный текст, а не черновик

## Что этот skill делает

`ux-copy-editor` должен:

1. убрать AI-tone
2. убрать воду
3. убрать канцелярит
4. убрать повторения
5. убрать неуверенные и слабые конструкции
6. убрать лишнее объяснение
7. сделать смысл быстрее считываемым
8. сделать формулировку более естественной
9. сохранить product intent
10. усилить текст без потери функции
11. довести copy до release quality

## Основной workflow

### Шаг 1. Понять контекст
Перед редактурой определить:

- где находится текст
- в каком шаге user flow он появляется
- что пользователь в этот момент делает
- что пользователь должен понять
- что пользователь должен сделать дальше
- есть ли риск, ошибка, подтверждение, выбор или трение

Нельзя редактировать текст как изолированную фразу без понимания его функции в интерфейсе.

### Шаг 2. Определить функцию текста
Каждый текст должен выполнять одну главную функцию.

Обычно это:

- направить
- объяснить
- подтвердить
- предупредить
- ограничить ожидания
- помочь исправить ошибку
- снизить неопределённость
- запросить действие
- завершить действие

Если функция текста не ясна, сначала сделать ясной функцию, а потом формулировку.

### Шаг 3. Очистить текст
Убрать всё, что не помогает задаче текста:

- вводные фразы
- декоративные слова
- повторы
- размытую вежливость
- AI-style transitions
- пустые усилители
- лишние объяснения
- корпоративный шум
- разговорный мусор
- “friendly fluff”
- слабые шаблонные конструкции

Текст должен работать, а не производить впечатление.

### Шаг 4. Усилить формулировку
После очистки текст должен стать:

- короче
- яснее
- конкретнее
- увереннее
- полезнее для действия
- ближе к реальному UX-контексту

Если фразу можно сделать проще без потери смысла, её нужно упростить.

### Шаг 5. Проверить product intent
Редактура не должна ломать продуктовую логику.

Нельзя терять:

- важное ограничение
- причину ошибки
- условие действия
- следующую развилку
- уровень риска
- ожидание по результату
- доверие к системе

Если текст объясняет ограничение или управляет ожиданиями, его нельзя “украсить” ценой потери смысла.

### Шаг 6. Проверить release quality
Перед завершением проверить:

- сразу ли понятен смысл
- видно ли, что делать дальше
- нет ли двусмысленности
- нет ли лишней когнитивной нагрузки
- не звучит ли текст как AI
- не звучит ли он как корпоративный шаблон
- не слишком ли он длинный для своего места
- не скрывает ли важное за мягкой формулировкой
- можно ли реально выпускать этот текст в продукт

### Шаг 7. Вернуть финальную версию
Если задача только на редактуру, вернуть:

- финальный текст
- при необходимости 2–3 варианта, только если есть реальная UX-развилка:
  - shortest
  - balanced
  - more explicit

Не плодить варианты ради видимости работы.

## Правила сильного UX copy

Хороший текст:

- короткий, когда это возможно
- длиннее только когда это снижает непонимание
- конкретный
- сканируемый
- прямой
- естественный
- без лишней мягкости
- без бюрократии
- без искусственной дружелюбности
- без словесного тумана
- без декоративной “заботы”
- без overexplaining

Предпочтения:

- активные конструкции лучше пассивных
- конкретные глаголы лучше абстракций
- простые слова лучше усложнённых
- явное действие лучше размытого описания
- естественная человеческая фраза лучше polished AI-sentence

## Что особенно важно

### 1. Не звучать как AI
Убирать или жёстко проверять конструкции вроде:

- “Seamlessly...”
- “Easily...”
- “You can now...”
- “We’re here to help...”
- “Let’s get started...”
- “In order to...”
- “It looks like...”, если можно сказать точнее
- “Something went wrong”, если можно объяснить, что именно и что делать дальше

Отдельно — клише-контрасты через отрицание. Частый речевой тик модели, особенно в лендинг- и
продуктовом копи. Почти всегда переписывать в прямое утверждение:

- «не просто X — это Y»
- «не X, а Y»
- «это не про X, это про Y»
- «больше, чем просто X»
- «X? Забудьте. Теперь Y»

Контраст-отрицание маскирует отсутствие конкретики: оно сообщает, чем продукт **не** является,
вместо того чтобы сказать, что он делает. Вместо «не просто задачник, а система роста» — сказать
прямо, что продукт делает и для кого. Утверждение сильнее отрицания.

### 2. Не быть слишком милым
Не нужно:

- сюсюкать
- натягивать дружелюбие
- прятать ошибку за мягким тоном
- превращать простое действие в длинный conversational blob
- добавлять эмоцию там, где нужна ясность

### 3. Не быть сухим ради “профессиональности”
Текст не должен:

- звучать как policy
- звучать как legal boilerplate, если это не legal text
- быть перегруженным терминами
- требовать перечитывания
- создавать лишнюю дистанцию между продуктом и пользователем

### 4. Не маскировать плохой UX хорошей редактурой
Если проблема в самом flow, wording alone не решает задачу.

Если текст приходится чрезмерно объяснять, нужно явно отметить, что проблема может быть не только в copy, но и в UX, логике шага или интерфейсной структуре.

## Что запрещено

- не писать generic AI-copy
- не делать текст “красивым”, если он становится слабее
- не терять конкретику
- не упрощать до потери смысла
- не скрывать product risk
- не прятать плохую механику за косметикой
- не считать “звучит нормально” критерием готовности
- не выпускать weak copy как done

## Хороший результат

Хороший результат — это когда:

- текст звучит естественно
- текст быстро считывается
- текст помогает действию
- текст не раздражает
- текст не шумит
- текст не выглядит AI-generated
- текст сохраняет продуктовый смысл
- текст соответствует quality bar системы
- текст можно спокойно отправлять на user review или release

## Формат поведения

Контекст ->
функция текста ->
очистка ->
сжатие ->
усиление ->
product intent check ->
release quality check ->
финальный вариант

## Критерий хорошей работы

Хорошая работа — это не когда текст стал “приятнее”.

Хорошая работа — это когда user-facing copy стала:

- яснее
- короче
- точнее
- естественнее
- сильнее
- полезнее
- релизно готовой
