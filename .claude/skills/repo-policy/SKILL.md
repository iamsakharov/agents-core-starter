# repo-policy

Слой agents-core — среда разработчика, а не артефакт репозитория. Он не должен уезжать
в репозитории, где работает кто-то ещё: в git нет прав на уровне файлов, всё закоммиченное
видно каждому, у кого есть доступ, вместе со всей историей.

Этот skill запускает `scripts/repo-policy.sh` — явную пометку репозитория и проверку
на личные следы.

## Когда использовать

- перед тем как добавить человека в свой репозиторий
- перед передачей репозитория в чужой контур или организацию
- при первой работе в рабочем, клиентском или чужом репо
- когда нужно ответить на вопрос «что увидит тот, кому я дам доступ»
- когда пользователь просит проверить репозиторий на личные данные

## Как запускать

Найди скрипт в таком порядке и запусти первый существующий:

1. `$AGENTS_CORE_SRC/scripts/repo-policy.sh`
2. `~/Dev/agents-core/scripts/repo-policy.sh`
3. `scripts/repo-policy.sh` в текущем репозитории

```bash
bash <путь>/repo-policy.sh check      # только проверить, ничего не менять
bash <путь>/repo-policy.sh status     # показать текущую метку
bash <путь>/repo-policy.sh shared     # репо доступен другим → вендоринг запрещён
bash <путь>/repo-policy.sh none       # слой сюда не кладём вообще
bash <путь>/repo-policy.sh personal   # мой единоличный репо → вендоринг разрешён
```

Вторым аргументом можно передать папку репозитория, если работаешь не из неё.

Без аргументов — режим `check`. По умолчанию запускай именно `check`: он ничего не меняет.
Метку ставь только когда пользователь этого явно попросил или явно подтвердил.

## Что делает метка

`git config --local agents-core.policy` — локальная запись в `.git/config`. В репозиторий
она не коммитится, коллеги её не видят. `sync.sh` читает её раньше всех автопроверок:
`shared` и `none` — отказ вендорить слой, `personal` — обычный путь (автопроверки по
владельцу и коллабораторам при этом остаются).

Для `shared` и `none` команда дополнительно прописывает пути слоя в `.git/info/exclude` —
локальный ignore, который тоже не коммитится.

## Что показывает проверка

- кто имеет доступ к репозиторию (коллабораторы и висящие приглашения)
- закоммичены ли файлы слоя (`.claude/`, `.cursor/`, `CLAUDE.md`, `AGENTS.md`, `.mcp.json`)
- не попал ли в индекс `.claude/settings.local.json` — личный allowlist
- личные следы в трекаемых файлах: логин, почта, домашние пути
- то же самое **в истории** — её видит каждый, у кого есть доступ

## Как интерпретировать результат

Скрипт ничего не удаляет и не коммитит — он печатает находки и команды. Это осознанно:
в общем репозитории часть файлов может принадлежать не тебе (например `launch.json` коллеги),
и решение, что убирать, принимает человек.

Разбирая вывод:

- **находки только в текущем состоянии** — чинятся `git rm --cached` и коммитом;
- **находки в истории** — `git rm` их не прячет. Если репозиторий уходит другим, правильный
  ответ обычно не «переписать историю», а «передать новый репозиторий с чистой историей».
  Переписывание (`git filter-repo` + force-push) ломает существующие клоны и меняет все SHA —
  предлагать его можно, только показав эту цену и получив явное согласие;
- **чужие файлы среди находок** — не трогать молча, сначала показать пользователю.

После проверки дай короткий вывод: что увидит человек с доступом, что стоит убрать,
и нужна ли метка.
