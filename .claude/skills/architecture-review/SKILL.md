# architecture-review

Используй этот skill, когда нужно проверить качество архитектуры до, во время или после execution.

Это не implementation skill.
Это quality-control layer, который проверяет, выдерживает ли решение нагрузку, рост сложности, дальнейшие изменения и реальные сценарии использования.

## Назначение

Этот skill нужен, чтобы не пропускать решения, которые:

- выглядят рабочими только локально
- решают симптом, а не структуру
- плохо масштабируются
- смешивают ответственности
- создают скрытую сложность
- создают хрупкие зависимости
- разваливаются при следующем изменении
- выглядят “быстро сделанными”, но дорого обойдутся потом

Главная задача:
отделять реально сильную архитектуру от временно работающей конструкции.

## Когда использовать

Используй этот skill, когда:

- проектируется новая система
- меняется существующая архитектура
- добавляется новая важная feature
- появляется сложный flow
- требуется review implementation plan
- задача затрагивает несколько модулей
- решение меняет data flow
- решение добавляет новые dependencies
- есть ощущение, что решение слишком “хитрое”
- нужно проверить, не взят ли плохой shortcut
- нужно понять, можно ли безопасно идти в implementation
- этап завершён и нужен structural review перед closure

## Роль в общей системе

`architecture-review` работает как structural review layer внутри core workflow:

- planning формирует задачу
- execution предлагает или реализует решение
- `architecture-review` проверяет структуру
- reviewer оценивает итоговое качество этапа
- refinement исправляет найденные слабости
- release идёт только после прохождения review слоя

Если решение меняет структуру системы, его нельзя считать качественным без архитектурной проверки.

## Что считать архитектурой

Архитектура в рамках этого skill включает:

- boundaries между частями системы
- separation of concerns
- data flow
- dependency structure
- module responsibilities
- orchestration logic
- state ownership
- integration surfaces
- extension paths
- operational complexity
- maintainability
- observability
- failure behavior
- changeability under future iterations

Это не только “большая системная архитектура”.
Даже локальный flow может быть архитектурно слабым.

## Основные вопросы review

### 1. Правильно ли определены границы
Нужно проверить:

- где начинается и заканчивается ответственность каждого блока
- нет ли смешения доменов
- нет ли утечек логики между слоями
- не зависит ли один слой от деталей другого без необходимости

Если границы размыты, система почти всегда начинает расти хаотично.

### 2. Правильно ли разложены ответственности
Проверить:

- у каждого ли блока есть ясная роль
- нет ли “god object” или “god module”
- не делает ли один компонент слишком много
- не лежит ли orchestration, state, validation и rendering в одном месте без причины

Если одна часть делает всё, это слабая архитектура, даже если она пока работает.

### 3. Не построено ли решение на shortcut
Нужно проверить:

- не является ли решение временным костылём, выданным за архитектуру
- не прячется ли важная логика в неудобном месте
- не появилась ли зависимость, которая потом будет мешать
- не решается ли структурная проблема локальным патчем

Shortcut допустим только если он честно обозначен как временный и управляемый.

### 4. Масштабируется ли решение
Проверить:

- что будет при росте числа сценариев
- что будет при росте сущностей
- что будет при росте ролей
- что будет при добавлении новых шагов
- что будет при изменении требований
- не потребует ли следующее изменение переписывания половины решения
Если решение ломается от следующей реальной итерации, оно слабое.

### 5. Управляется ли сложность
Проверить:

- где концентрируется сложность
- оправдана ли она
- можно ли сделать проще
- не спрятана ли сложность под “умной” структурой
- сможет ли следующий человек быстро понять, как это работает

Сложность допустима только если она неизбежна и собрана аккуратно.

### 6. Ясный ли data flow
Нужно понимать:

- откуда приходят данные
- кто ими владеет
- кто их меняет
- кто их читает
- где источник истины
- где возможны рассинхроны
- где могут появиться побочные эффекты

Если data flow не объясняется просто, почти всегда есть архитектурный риск.

### 7. Есть ли опасные связности
Проверить:

- нет ли tight coupling
- нет ли скрытых зависимостей
- не появились ли циклические зависимости
- не завязан ли один модуль на детали другого
- можно ли тестировать и менять части независимо

Чем сильнее сцепление, тем выше цена изменений.

### 8. Продуман ли failure behavior
Нужно проверить:

- что происходит при ошибке
- что происходит при partial failure
- что происходит при недоступности зависимости
- можно ли безопасно восстановиться
- не теряется ли состояние
- не создаётся ли тихая поломка

Архитектура без failure thinking не завершена.

### 9. Поддерживает ли решение дальнейшую работу
Проверить:

- удобно ли это развивать
- удобно ли это дебажить
- удобно ли это review-ить
- удобно ли это тестировать
- удобно ли это передавать дальше
- не превращает ли текущее решение каждую следующую задачу в более дорогую

## Основной workflow

### Шаг 1. Понять, что именно review-ится
Сначала определить:

- это architecture of system, feature, flow or module
- это proposed design или already implemented solution
- это initial design review или post-implementation review
- какие ограничения уже есть
- какие parts являются критичными

### Шаг 2. Вытащить структуру решения
Ясно разложить:

- основные части
- роли частей
- связи между ними
- направления данных
- orchestration points
- места принятия решений
- места роста сложности

Если структура не может быть объяснена ясно, значит она либо не собрана, либо уже перегружена.

### Шаг 3. Найти structural risks
Искать:

- смешение ответственностей
- плохие boundaries
- shortcut thinking
- hidden coupling
- future rewrite traps
- local optimization вместо системного решения
- overengineering
- under-structuring
- complexity leaks

### Шаг 4. Проверить changeability
Спросить:

- что будет, если завтра появится новый сценарий
- что будет, если сущностей станет больше
- что будет, если появится ещё одна роль
- что будет, если бизнес-логика изменится
- что будет, если одну часть надо заменить

Если ответ “придётся ломать всё рядом”, архитектура слабая.

### Шаг 5. Дать вердикт
Финальный вывод должен быть одним из:

- можно идти дальше
- можно идти дальше, но есть контролируемые риски
- нужно исправить архитектуру до следующего этапа
- решение локально работает, но структурно слабое
- нужен redesign части системы

## Что считать хорошей архитектурой

Хорошее решение — это когда:

- границы ясны
- роли частей понятны
- data flow читается
- сложность контролируется
- зависимости оправданы
- решение выдерживает следующую итерацию
- failure behavior хотя бы базово продуман
- сопровождение не становится кошмаром
- система не держится на хрупком знании автора

## Красные флаги

Плохой сигнал, если:

- один модуль делает слишком много
- orchestration размазана по системе
- state ownership непонятен
- важная логика спрятана в side effects
- следующий feature request почти гарантирует переписывание
- решение зависит от порядка случайных шагов
- нет ясного source of truth
- слишком много скрытой магии
- код или flow “работает”, но его трудно объяснить
- решение выглядит умно, но хрупко

## Что запрещено

- не путать working demo с сильной архитектурой
- не считать shortcut финальным решением без явной маркировки
- не игнорировать coupling
- не смешивать orchestration и implementation без причины
- не прятать системные проблемы под локальными патчами

- не пропускать review только потому, что “уже заработало”
- не выдавать сложность за глубину
- не одобрять решение, которое сломает следующую итерацию

## Формат поведения

Структура ->
границы ->
ответственности ->
data flow ->
dependencies ->
failure behavior ->
changeability ->
risks ->
verdict

## Критерий хорошей работы

Хорошая работа — это не когда review звучит умно.

Хорошая работа — это когда после review становится ясно:

- насколько решение реально надёжно
- где его слабые места
- какие риски допустимы
- что нужно исправить сейчас
- можно ли безопасно двигаться дальше
