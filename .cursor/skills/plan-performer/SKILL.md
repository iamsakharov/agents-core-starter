# plan-performer

Используй этот skill, когда задача большая, многоэтапная или требует строгого исполнения по этапам.

## Назначение

Этот skill задаёт жёсткий execution workflow:

1. большая задача не идёт одним прогоном
2. сначала задача должна быть разобрана и структурирована
3. затем работа идёт по этапам
4. на каждый этап формируется отдельный prompt
5. этапы исполняются раздельно
6. после этапов идёт review
7. если есть замечания, запускается refinement loop
8. только после review и апрува пользователя задача или этап закрываются

## Когда использовать

Используй этот skill, когда:

- задача слишком большая для одного prompt
- задача состоит из нескольких этапов
- есть зависимости между частями работы
- нужно держать контекст чистым
- есть риск giant one-shot run
- задача является частью roadmap item или эпика
- нужно провести задачу через planning -> execution -> review -> refinement

## Общая логика

Этот skill не заменяет subagents.
Он задаёт порядок работы и заставляет систему не сваливаться в хаос.

## Основной workflow

### Шаг 1. Получить структуру задачи
Если задача ещё не декомпозирована:

- сначала использовать `plan-orchestrator`
- если задача уже является roadmap item, при необходимости сначала использовать `roadmap-task-analyzer`
- если задача часть большого направления, при необходимости сначала использовать `epic-master`

Нельзя начинать execution большого объёма без структуры.

### Шаг 2. Разбить на этапы
После planning слоя должна быть понятна структура:

- этапы
- зависимости
- волны исполнения
- отдельные задачи
- отдельные prompts

### Шаг 3. Выполнять по этапам
Каждый этап должен исполняться отдельно.

Нельзя:

- сливать все этапы в один run
- давать один огромный prompt на всё
- смешивать несколько независимых задач в одну execution массу

### Шаг 4. Подбирать правильный subagent type
Используй подходящий тип под характер этапа:

- `explore` — если нужно исследование, поиск файлов, карта зависимостей, чтение контекста
- `generalPurpose` — если нужен основной implementation
- `shell` — если нужны tests, lint, scripts, migrations, git, terminal-heavy действия
- `reviewer` — если этап завершён и нужен quality review
- `refinement-agent` — если после review или комментариев пользователя появились замечания и доработки
- `roadmap-task-status` — если нужно быстро понять статус большого item
- `epic-master` — если execution начинает терять связь с большим эпиком

### Шаг 5. Отдельный prompt на каждую задачу
Каждая задача внутри этапа должна получать отдельный prompt.

Prompt должен быть:

- отдельным
- конкретным
- ограниченным по scope
- ориентированным на результат
- понятным следующей сущности

### Шаг 6. Review после исполнения
После завершения этапа или значимой задачи обязательно запускать `reviewer`.

Review должен ответить:

- решена ли задача
- нет ли мусора
- не взято ли слабое shortcut решение
- масштабируется ли результат
- можно ли двигаться дальше
- нужен ли refinement

### Шаг 7. User approval
После review результат идёт пользователю.

Если пользователь говорит:
- “ок” -> этап или задача закрываются
- даёт замечания -> замечания идут в `refinement-agent`

### Шаг 8. Refinement loop
Если есть замечания от reviewer или пользователя:

- не терять их
- не смешивать их с уже закрытой частью
- превращать их в новую итерацию
- запускать следующий refinement cycle

### Шаг 9. Closure
После принятия результата:

- зафиксировать, что закрыто
- что осталось
- что ушло в следующую итерацию
- при необходимости подготовить `release-summary`

## Что запрещено

- не делать большую задачу одним гигантским прогоном
- не пропускать planning слой
- не смешивать planning, implementation и review
- не пропускать review
- не считать “код написан” критерием завершения
- не терять замечания пользователя
- не терять follow-up между итерациями

## Что считать хорошим исполнением

Хорошее исполнение — это когда:

- задача декомпозирована
- этапы понятны
- execution идёт по отдельным prompts
- review обязателен
- замечания превращаются в новую итерацию, а не в хаос
- closure понятен
- основной контекст не превращён в мусор

## Формат поведения

Большая задача ->
planning ->
этапы ->
отдельные prompts ->
раздельное исполнение ->
review ->
user approval ->
либо closure, либо refinement loop.

## Критерий хорошей работы

Хороший результат — это когда система не просто “что-то сделала”, а провела задачу через управляемый цикл до качественного результата.
