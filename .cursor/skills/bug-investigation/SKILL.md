# bug-investigation

Используй этот skill, когда нужно не просто “попробовать пофиксить баг”, а провести нормальное расследование проблемы.

Это не quick-fix skill.
Это diagnostic layer, который не даёт системе хаотично патчить симптомы вместо поиска реальной причины.

## Назначение

Этот skill нужен, чтобы:

- не гадать о причине бага
- не чинить вслепую
- не смешивать симптомы и root cause
- не делать случайные изменения “на удачу”
- не плодить регрессии
- не тратить время на хаотичный debug
- превращать проблему в управляемый investigation flow

Главная задача:
понять, что именно сломано, почему это сломано, как это проверить и как исправить без лишнего ущерба.

## Когда использовать

Используй этот skill, когда:

- есть баг
- есть flaky behavior
- есть intermittent issue
- есть race condition suspicion
- есть inconsistent state
- есть unexpected UI behavior
- есть failing tests без ясной причины
- есть production issue
- есть логическая ошибка
- есть side effect, который непонятно откуда пришёл
- есть regression
- есть data mismatch
- есть integration issue
- есть проблема, где возможны несколько причин

Если причина ещё не установлена, этот skill почти всегда нужен.

## Роль в общей системе

`bug-investigation` работает как disciplined diagnostic workflow внутри core system:

- проблема зафиксирована
- `bug-investigation` проводит расследование
- после установления причины идёт fix planning или implementation
- затем review
- затем, при необходимости, refinement
- closure возможен только после подтверждения, что проблема реально понята и исправлена

Нельзя считать баг “обработанным”, если был сделан патч без ясного понимания причины.

## Основной принцип

Не начинать с фикса.
Начинать с понимания.

Порядок должен быть таким:

symptom ->
reproduction ->
evidence ->
hypotheses ->
verification ->
root cause ->
fix approach ->
validation

## Основной workflow

### Шаг 1. Зафиксировать симптом
Сначала нужно чётко описать:

- что именно происходит
- что ожидалось вместо этого
- где это проявляется
- когда это проявляется
- у кого это проявляется
- насколько это стабильно воспроизводится
- какая цена ошибки

Нельзя расследовать “что-то не так”.
Симптом должен быть назван ясно.

### Шаг 2. Собрать условия воспроизведения
Определить:

- как воспроизвести проблему
- воспроизводится ли она стабильно
- есть ли конкретная последовательность шагов
- есть ли environment-specific conditions
- зависит ли она от данных, роли, тайминга, сети, состояния приложения
- можно ли сузить problem surface

Если точного repro ещё нет, это нужно честно отметить и отдельно работать над repro.

### Шаг 3. Собрать evidence
Нужно собирать факты, а не мнения:

- logs
- stack traces
- console output
- failing tests
- timestamps
- network responses
- state snapshots
- relevant code paths
- related changes
- recent regressions
- error boundaries
- observed side effects

Не строить диагноз раньше сбора evidence.

### Шаг 4. Разделить symptom и cause
Очень важно различать:

- что является наблюдаемым проявлением
- что является предположительной причиной
- что является только коррелирующим сигналом

Частая ошибка — принять первое заметное отклонение за root cause.

### Шаг 5. Построить гипотезы
После evidence сформировать ограниченный список рабочих гипотез:

- какие причины наиболее вероятны
- какие причины возможны, но слабее
- что может быть только побочным эффектом
- какие hypotheses можно быстро проверить
- какие hypotheses требуют deeper trace

Гипотезы должны опираться на evidence, а не на интуитивное “обычно это вот это”.

### Шаг 6. Проверить гипотезы по одной

Каждую гипотезу проверять отдельно.

Нельзя:

- менять сразу несколько вещей
- смешивать несколько potential fixes
- терять контроль над тем, что именно подтвердило или опровергло гипотезу
- проводить debugging как беспорядочную серию случайных действий

Каждый шаг должен уменьшать неопределённость.

### Шаг 7. Установить root cause
Root cause можно считать установленной, если ясно:

- какая именно часть системы ломается
- при каких условиях
- почему это приводит к симптому
- какая цепочка причинности
- почему проблема проявлялась именно так
- какие альтернативные объяснения уже исключены

Если это не установлено, значит расследование ещё не закончено.

### Шаг 8. Сформировать правильный fix approach
Только после root cause определить:

- где лучше исправлять проблему
- нужен ли локальный fix или structural correction
- есть ли риск regression
- нужны ли guardrails
- нужны ли tests
- нужны ли instrumentation / logs / assertions
- не маскирует ли proposed fix более глубокую проблему

### Шаг 9. Подтвердить исправление
После фикса нужно проверить:

- баг реально исчез
- symptom больше не проявляется
- root cause закрыта
- не появилось новых проблем
- есть ли regression protection
- можно ли считать проблему закрытой

## Что считать хорошим расследованием

Хорошее investigation — это когда:

- симптом описан ясно
- repro либо найден, либо его отсутствие честно зафиксировано
- evidence собрано
- гипотезы ранжированы
- случайные действия исключены
- root cause установлена или границы неизвестности сужены
- fix основан на понимании, а не на удаче
- результат можно объяснить другому человеку

## Красные флаги

Плохой сигнал, если:

- fix делают до понимания причины
- гипотезы меняются хаотично
- меняют несколько вещей сразу
- symptom путают с cause
- нет ясного repro
- нет evidence trail
- причина объявлена “скорее всего”
- баг “исчез”, но никто не понял почему
- proposed fix только прячет проявление
- investigation превращается в random walk по коду

## Что запрещено

- не гадать
- не патчить вслепую
- не объявлять root cause без доказательств
- не менять несколько переменных одновременно без причины
- не выдавать исчезновение симптома за доказанное решение
- не игнорировать возможность regression
- не путать correlation и causation
- не заканчивать расследование на “ну вроде заработало”

## Если баг UI / UX
Если проблема в интерфейсе, дополнительно проверять:

- state transitions
- loading timing
- stale state
- async race
- visibility conditions
- role-based rendering
- invalid assumptions in flow
- mismatch between displayed state and real state

## Если баг data / backend / integration
Дополнительно проверять:

- source of truth
- request/response chain
- schema assumptions
- retries
- idempotency
- async processing
- ordering issues
- stale cache
- partial writes
- integration contract mismatches

## Формат поведения

Symptom ->
repro ->
evidence ->
hypotheses ->
verification ->
root cause ->
fix approach ->
validation

## Критерий хорошей работы

Хорошая работа — это не когда баг “как будто исчез”.

Хорошая работа — это когда:
- причина реально понята
- исправление опирается на доказательства
- риск повторения снижен
- решение можно объяснить
- систему не пришлось лечить хаотичными патчами
