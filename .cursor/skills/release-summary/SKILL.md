# release-summary

Используй этот skill, когда задача, этап, refinement cycle или релизная итерация завершены и результат нужно собрать в короткий, рабочий и decision-friendly summary.

Это не decorative recap.
Это closure layer, который фиксирует результат так, чтобы не терялись изменения, статус, риски и следующий шаг.

## Назначение

Этот skill нужен, чтобы:

- не терять итог после execution
- не оставлять завершённую работу без фиксации
- не размывать, что реально сделано
- не путать finished, partial и pending
- не терять риски, ограничения и follow-up
- давать понятный closure после этапа или релиза

Главная задача:
собрать завершённый кусок работы в краткий итог, с которым можно продолжать дальше без потери контекста.

## Когда использовать

Используй этот skill, когда:

- завершён этап
- завершена задача
- завершён refinement cycle
- завершён implementation pass
- завершён reviewable chunk of work
- завершён релизный блок
- нужно передать результат пользователю
- нужно зафиксировать closure
- нужно сформировать handoff summary
- нужно быстро показать status after change

Если что-то реально завершилось и контекст нельзя потерять, этот skill уместен.

## Роль в общей системе

`release-summary` работает как closure layer внутри core workflow:

- planning определяет задачу
- execution делает работу
- review оценивает результат
- refinement исправляет замечания
- user approval подтверждает принятие
- `release-summary` фиксирует итог, статус, риски и следующий шаг

Без closure даже хорошая работа начинает расползаться в памяти и теряет operational clarity.

## Что этот skill должен фиксировать

Хороший release summary должен отвечать на вопросы:

- что именно было сделано
- что именно изменилось
- что теперь работает иначе
- что не было сделано
- что осталось открытым
- есть ли риски или caveats
- что логично делать следующим шагом

Не всё сразу и не длинно.
Только то, что реально нужно для продолжения работы.

## Основной workflow

### Шаг 1. Определить scope завершения
Сначала понять:

- summary делается по задаче, этапу, итерации или релизу
- что именно считается завершённым
- это full completion или partial completion
- что было в scope
- что оказалось out of scope

Нельзя писать summary без ясных границ.

### Шаг 2. Зафиксировать результат
Коротко и конкретно назвать:

- какие изменения внесены
- какие части обновлены
- какие проблемы закрыты
- какие решения приняты
- что теперь находится в новом состоянии

Нужно говорить о фактическом результате, а не о процессе ради процесса.

### Шаг 3. Отделить done от not done
Ясно разделить:

- что завершено
- что частично сделано
- что не сделано
- что отложено
- что требует отдельной следующей итерации

Это обязательный шаг.
Иначе summary создаёт ложное ощущение завершённости.

### Шаг 4. Отметить риски и caveats
Если есть ограничения, нужно указать:

- что осталось хрупким
- что не проверено полностью
- где есть технический долг
- где есть временное решение
- где нужна дополнительная валидация
- где есть dependency на следующий шаг

Коротко, без драматизации, но честно.

### Шаг 5. Сформулировать следующий шаг
Хороший summary должен закрывать вопрос:
**что теперь логично делать дальше.**

Это может быть:

- следующий этап
- review
- user validation
- rollout
- bugfix iteration
- follow-up task
- architecture correction
- research continuation
- documentation update

### Шаг 6. Подать результат компактно
Summary должен быть:

- коротким
- сканируемым
- без воды
- без повторов
- без лишней самооценки
- без “мы проделали большую работу”
- без театральной упаковки

## Рекомендуемая структура

Если формат не задан, по умолчанию summary стремится к структуре:
1. done
2. changed
3. not done / pending
4. risks / caveats
5. next step

## Что считать хорошим release summary

Хороший summary — это когда:

- за 30–60 секунд ясно, что произошло
- не возникает ложной завершённости
- видно, что реально изменилось
- видны открытые края
- виден следующий шаг
- можно безопасно продолжать работу без потери нити

## Красные флаги

Плохой сигнал, если:

- summary длиннее самой сути
- много процесса, мало результата
- непонятно, что реально завершено
- скрыты недоделки
- нет следующего шага
- summary звучит “успокаивающе”, но неинформативно
- читатель после summary всё равно не понимает статус
- текст замазывает риски

## Что запрещено

- не выдавать partial work за finished
- не скрывать caveats
- не пересказывать весь процесс
- не раздувать значимость
- не путать summary и changelog dump
- не делать vague wording вроде “улучшено”, если можно сказать точнее
- не заканчивать без operational next step
- не создавать фальшивое ощущение closure

## Если summary идёт пользователю
Особенно важно:

- писать коротко
- отделять факт от оценки
- не перегружать внутренними деталями
- показать ценность изменения
- показать, что осталось
- показать, что нужно от пользователя, если это нужно

## Если summary внутренний
Можно сильнее акцентировать:

- structural changes
- risks
- debt
- follow-up dependencies
- next implementation slice

## Формат поведения

Scope ->
done ->
changed ->
not done ->
risks ->
next step

## Критерий хорошей работы

Хорошая работа — это не когда summary “звучит солидно”.

Хорошая работа — это когда после summary:
- статус ясен
- результат понятен
- недоделки не потеряны
- риски не скрыты
- следующий шаг очевиден
- контекст не распадается
