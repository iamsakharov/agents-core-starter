# ui-ux-foundation

Используй этот skill, когда задача затрагивает:

- интерфейсы
- экраны
- состояния
- user flows
- admin flows
- navigation
- interaction logic
- dashboard structures
- forms
- settings
- product UX
- layout decisions
- visual hierarchy
- information architecture на уровне интерфейса

Это не про “сделать красиво”.
Это baseline discipline skill, который не даёт системе производить слабый UI и рыхлый UX.

## Назначение

Этот skill задаёт минимальный стандарт качества для всех UI/UX-решений.

Он нужен, чтобы система:

- не генерировала хаотичные интерфейсы
- не смешивала разные роли и сценарии
- не перегружала экран
- не прятала главное среди второстепенного
- не делала “pretty but unclear” решения
- не строила flow без ясной user intent
- не делала UI отдельно от product logic
- не подменяла UX декоративностью

## Когда использовать

Используй этот skill, когда:

- проектируется новый экран
- меняется существующий экран
- создаётся dashboard
- создаётся admin panel
- продумывается onboarding
- проектируется settings area
- меняется navigation
- создаётся форма
- добавляется новый user flow
- проектируется error / empty / loading state
- обсуждается структура интерфейса
- нужно оценить, не сломан ли UX
- задача касается продукта, который будет трогать пользователь

Если решение увидит пользователь, этот skill почти всегда релевантен.

## Роль в общей системе

`ui-ux-foundation` не заменяет product thinking, research или implementation.

Он задаёт UX baseline внутри общей системы:

- planning определяет задачу
- research даёт контекст
- architecture определяет структуру
- `ui-ux-foundation` проверяет, что интерфейс и flow не деградируют
- implementation реализует решение
- review оценивает качество
- refinement исправляет замечания

Это guardrail skill.
Он нужен, чтобы даже в быстрых итерациях качество UX не разваливалось.

## Основные принципы

### 1. Product intent first
Интерфейс всегда должен обслуживать конкретную продуктовую задачу.

Сначала определить:

- кто пользователь
- что он пытается сделать
- что для него главное
- что вторично
- что является success state
- где есть трение, риск, неопределённость или цена ошибки

Нельзя проектировать экран без ясного ответа на вопрос:
**зачем этот интерфейс существует и что он должен помогать сделать.**

### 2. One screen = one primary job
У каждого экрана должна быть главная работа.

Если экран пытается одновременно:
- продавать
- объяснять
- настраивать
- показывать аналитику
- управлять сущностями
- обучать

то почти всегда он начинает расползаться.

Нужно чётко различать:
- primary action
- supporting information
- secondary actions
- advanced controls

### 3. Не смешивать роли и контексты
Одна из самых частых ошибок — смешивать:

- user flow и admin flow
- primary task и support task
- consumption и configuration
- overview и editing
- daily operations и rare edge cases

Если сценарии разные по цели, частоте или уровню ответственности, их нельзя небрежно сваливать в один UX-контур.

### 4. Visual hierarchy должна быть управляемой
Пользователь должен быстро понимать:

- где главное
- что требует внимания
- что можно сделать сейчас
- что вторично
- что опасно
- что завершено
- что заблокировано

Если всё кричит одинаково, не кричит ничего.

### 5. UI не должен объяснять плохую структуру
Если экран требует слишком много текста для объяснения, проблема часто не в копирайте, а в логике интерфейса.

Нельзя лечить:
- плохую IA
- слабый flow
- смешанные роли
- перегрузку controls
- неясную навигацию

только дополнительным текстом.

### 6. Состояния обязательны
Нельзя думать только в happy path.

Нужно проектировать:
- empty state
- loading state
- success state
- error state
- partial state
- locked / unavailable state
- destructive action confirmation
- permission state, если роли различаются

Если состояние не продумано, UX не завершён.

## Основной workflow

### Шаг 1. Определить пользователя и роль
Сначала понять:

- кто основной пользователь
- какая у него роль
- какой у него контекст
- насколько часто он делает это действие
- насколько он компетентен
- насколько дорого ему ошибиться

### Шаг 2. Определить primary job
Для экрана, блока или flow определить:

- что пользователь должен сделать
- что он должен понять
- какое действие главное
- что является успешным исходом

Если это не сформулировано в одном ясном предложении, дизайн-рамка ещё слабая.

### Шаг 3. Разделить primary и secondary
Разложить:

- primary content
- primary action
- supporting info
- secondary actions
- rare actions
- dangerous actions
- admin-only functions

Если всё лежит в одной плоскости, значит структура ещё не собрана.

### Шаг 4. Проверить flow
Нужно проверить:

- есть ли логичная последовательность
- понятно ли, куда идти дальше
- есть ли лишние шаги
- можно ли сократить friction
- не прячется ли важное решение слишком глубоко
- не создаёт ли интерфейс лишнюю когнитивную нагрузку

### Шаг 5. Проверить states
Для каждой важной точки спросить:

- что видит пользователь, если данных нет
- что происходит, пока данные грузятся
- что происходит при ошибке
- что происходит после успеха
- что происходит, если доступ ограничен
- что происходит, если действие опасное или необратимое

### Шаг 6. Проверить иерархию и ясность
Финально оценить:

- видно ли главное с первого взгляда
- не перегружен ли экран
- не слишком ли много CTA
- есть ли конфликт приоритетов
- не требует ли UI лишнего чтения
- не приходится ли пользователю “разгадывать” интерфейс

## Что считать хорошим UI/UX решением

Хорошее решение — это когда:

- задача экрана ясна
- пользовательский сценарий понятен
- роли не смешаны
- важное видно сразу
- второстепенное не мешает
- состояние системы считывается быстро
- количество решений на экран контролируется
- пользователь понимает, что делать дальше
- интерфейс не требует лишних объяснений
- визуальная структура поддерживает product logic

## Красные флаги

Плохой сигнал, если:

- экран пытается делать слишком много
- admin и user функции лежат рядом без причины
- важные действия не отличаются от второстепенных
- destructive actions не выделены
- UX держится на длинных пояснениях
- один и тот же блок решает разные задачи
- empty/loading/error states не продуманы
- форма требует лишних данных
- dashboard становится “свалкой карточек”
- layout кажется красивым, но непонятно, как им пользоваться

## Что запрещено

- не смешивать user и admin контуры без прямой причины
- не проектировать экран без primary job
- не перегружать интерфейс ради “функциональности”
- не прятать важное в визуальном шуме
- не полагаться на copy как замену слабой UX-структуре
- не игнорировать состояния
- не делать CTA равнозначными, если они не равны по важности
- не делать decisions based only on aesthetics
- не считать “выглядит нормально” критерием качества

## Если задача касается dashboard
Для dashboard особенно проверять:

- это overview или workspace
- это monitoring или action surface
- что главное число или главный сигнал
- какие действия частые
- какие действия редкие
- что требует внимания прямо сейчас
- что можно спрятать глубже
- не превращается ли dashboard в dump всего сразу

## Если задача касается form
Для form особенно проверять:

- каждое поле действительно нужно или нет
- что обязательно, а что нет
- можно ли сократить число решений
- понятны ли labels
- есть ли sensible defaults
- понятны ли validation messages
- что происходит после submit
- есть ли риск ошибки или потери данных

## Если задача касается settings
Для settings особенно проверять:

- разделены ли настройки по смыслу
- что меняется часто, а что редко
- что опасно
- что влияет на других пользователей
- что требует подтверждения
- не смешаны ли базовые и advanced controls

## Формат поведения

Пользователь ->
роль ->
primary job ->
flow ->
states ->
hierarchy ->
separation of concerns ->
final UI/UX judgment

## Критерий хорошей работы

Хорошая работа — это когда интерфейс не просто “выглядит лучше”.

Хорошая работа — это когда:
- структура стала сильнее
- сценарий стал яснее
- трение стало ниже
- роли разделены правильно
- приоритеты читаются быстрее
- интерфейс помогает действию, а не мешает ему
- решение можно безопасно передавать в implementation и review
